<objective>
Persist markdown notes on the Client entity and expose read/write HTTP endpoints. Add three additive columns to model Client (mirroring BoardCard's notes shape), a thin all-roles read endpoint, and a PM/ADMIN-gated write endpoint that stamps attribution and emits the app's first audited notes-write to the tamper-evident audit log. Backend-only: do NOT touch any frontend file (Phases 2 and 3 own those). Prove the behavior with a route-level RBAC/audit/isolation test.

Six open questions resolved (rationale one-liners):
1. Router placement — extend schedule.ts INLINE next to the existing `// ── Clients ──` section (schedule.ts:565). Rationale: schedule.ts is un-decomposed (team-members, assignments, absences, holidays, clients all inline); the board.ts→boardNotes.ts sub-router split exists only because board.ts was decomposed, which schedule.ts was not — do not introduce a split unprompted.
2. Write verb — PUT. Rationale: local consistency with the existing PUT /clients/:id in the same router beats cross-feature consistency with boardNotes.ts's PATCH; all client mutations stay on one verb.
3. Read response shape — thin { notes, notesUpdatedAt, notesUpdatedBy } (mirrors boardNotesService.updateNotes's own select). Rationale: Phase 2's modal already holds id/name/color from the bulk list; Phase 3 widens boardService's client select instead of calling this endpoint. No id/name/color duplication here.
4. notesUpdatedBy — stored as the raw req.session.userId, NO Prisma relation, matching BoardCard's deliberate relation-less design. Rationale: keeps the migration additive and avoids cascade noise; display-name resolution is explicitly Phase 2's problem — this phase neither solves nor blocks it.
5. Deploy-script mismatch — recorded only, NOT fixed (out of scope). launcher.sh uses `prisma db push`; launch-local.sh uses `migrate deploy`. The additive 3-column change is safe under both (db push reads schema.prisma, not migration history), so there is no functional risk; the only visible effect is that _prisma_migrations may not show the new row in production.
6. Socket invalidation — none. Rationale: the three existing /clients mutations in schedule.ts emit no invalidation; follow that directly-analogous precedent, not team-members' emitScheduleInvalidate.
</objective>
