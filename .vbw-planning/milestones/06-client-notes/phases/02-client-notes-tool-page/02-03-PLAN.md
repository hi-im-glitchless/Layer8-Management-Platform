<objective>
Build the user-facing Client Notes tool: a PM/ADMIN-only Tools sidebar entry, a route guarded by the existing RoleProtectedRoute, a client-list page, and a per-client modal that reuses the shared NotesEditor (from plan 02-01) and the client-notes hooks (from plan 02-02) to view/edit/save notes with live attribution. Wave 2: depends on 02-01 (NotesEditor at @/components/NotesEditor with the onSave contract) and 02-02 (useClientNotes/useUpdateClientNotes). Frontend-only; backend untouched. The modal shows name + colour only — no projects.

Decisions resolved (rationale one-liners):
1. Sidebar icon (research open Q5) — NotebookPen from lucide-react. Rationale: notes-writing semantics; not otherwise used in the sidebar, so no visual clash.
2. Modal open pattern (research page/modal patterns) — Board.tsx ?client={id} URL search param, not local useState. Rationale: many rows / one-open-at-a-time / deep-linkable; structural match to the board's card modal.
3. Name resolution + cross-feature import (research open Q7) — reuse board's useBoardMembers() and resolve id→name inline (displayName ?? username), passing the resolved name to NotesEditor; commented as an intentional cross-feature reuse (the endpoint is generic user data, requireAuth-only). Rationale: reuses the exact member-lookup path the roadmap mandates; avoids showing a raw id.
4. Route-guard test infrastructure (research open Q4) — treated as NEW, first-of-its-kind test infra (no existing route-guard/useAuth-role-variant pattern), sized as its own task, not a "reuse".
5. Deactivated/unknown editor — when useBoardMembers has no match, notesUpdatedBy resolves to null and NotesEditor already omits the "by X" clause. Rationale: matches the board's existing stale-id behavior; no extra fallback text.
</objective>
