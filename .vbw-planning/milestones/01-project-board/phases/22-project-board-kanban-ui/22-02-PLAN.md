## Objective
Build the two core visual components of the Kanban board: the column (droppable) and the card (draggable). These are self-contained components wired with @dnd-kit hooks but functional standalone (DnD context provided by parent in wave 2).

## Tasks

### Task 1: Create KanbanCard component
Create `frontend/src/features/board/components/KanbanCard.tsx`:

**Props:** `card: BoardCard`, `isDragOverlay?: boolean`, `onCardClick?: (cardId: string) => void`

**DnD:** Use `useDraggable({ id: card.id, data: { cardId: card.id, sourceStage: card.stage } })`. Apply `attributes`, `listeners`, `setNodeRef`. When `isDragging` is true, render with reduced opacity. When `isDragOverlay` is true, render with slight rotation + shadow for ghost effect.

**Layout (compact):**
- Outer: `flex overflow-hidden rounded-lg border bg-card shadow-sm cursor-grab` (cursor-grabbing when dragging)
- Left: color accent bar `w-1 shrink-0` with `style={{ backgroundColor: card.assignment?.projectColor }}`
- Right content `flex-1 p-3 space-y-1.5`:
  - Row 1: project name (`text-sm font-semibold leading-tight line-clamp-2`) + pin icon if `stageLockedBy && stageLockedBy !== 'auto'` (use `Pin` from lucide-react, `h-3 w-3 text-muted-foreground`)
  - Row 2: client name (`text-xs text-muted-foreground`) — only if `card.assignment?.client` exists
    > **Amendment (R01):** Client name row is deferred. Phase 21's BoardCard.assignment type does not include client fields. The row placeholder logic exists and will render once the assignment type is extended with client data in a future phase.
    > **Amendment (R02-QA):** The card-content truth "Cards show: project name, client name" is now realized via the Phase-24-R03 `Project` entity rather than the original per-assignment `projectName` / `assignment.client` shape. `KanbanCard.tsx` reads `card.project` for the project name and status (`card.project.status`) and `card.project.client?.name` for the client name. One card represents one Project, with a per-pentester assignment list — the per-assignment `projectName` model was superseded. Rationale: forward evolution introduced by the Phase-24 Project entity rework (commit `0d9ed2b`); one card = one Project is the canonical data shape. This supersedes and subsumes the R01 client-name deferral above, since client data now arrives via `card.project.client`. This formalizes the deviation recorded in 22-02-SUMMARY.
  - Row 3: checklist progress `{checked}/{total}` (`text-xs text-muted-foreground`) + status badge (reuse existing badge pattern: `text-[10px] font-medium px-1.5 py-0.5 rounded`)
- Click handler: call `onCardClick(card.id)` on card body click (not conflicting with drag — drag uses distance constraint)

**Wrap with `memo()`** comparing `card.id`, `card.stage`, `card.checklist`, `card.stageLockedBy`, `card.assignment?.projectName`.

### Task 2: Create KanbanColumn component
Create `frontend/src/features/board/components/KanbanColumn.tsx`:

**Props:** `stage: BoardStage`, `label: string`, `cards: BoardCard[]`, `cardCount: number`, `onCardClick?: (cardId: string) => void`

**DnD:** Use `useDroppable({ id: stage, data: { targetStage: stage } })`. Apply `setNodeRef` to the column body. Show visual feedback when `isOver` (e.g., border color change or subtle background highlight).

**Layout:**
- Outer: `w-80 flex-shrink-0 flex flex-col` (fixed width, full height)
- Header: stage label (`text-sm font-semibold text-muted-foreground uppercase tracking-wider`) + card count badge
- Body: `flex-1 overflow-y-auto space-y-2 p-2 rounded-lg bg-muted/30` (subtle background to delineate column area). When `isOver`, add `ring-2 ring-primary/50` highlight.
- Cards: map `cards` rendering `<KanbanCard>` for each
> **Amendment (R01-QA):** The MH-T06 truth "Cards sorted by `assignment.weekStart` ascending within each column" is satisfied at the board data layer, not inside KanbanColumn. KanbanColumn is intentionally a pure presentational renderer of its `cards` prop. Sorting is performed by `groupCardsByStage` in `frontend/src/features/board/types.ts` (sorts each stage group ascending by earliest `assignment.weekStart` via `localeCompare`; cards with no assignments sort last). The parent `frontend/src/routes/Board.tsx` calls `groupCardsByStage(filteredCards)` in a memo and passes the pre-sorted `cardsByStage[stage]` into `<KanbanColumn cards=...>`. Rationale: ordering belongs with data assembly so the column stays dumb and memo-friendly; this matches existing board conventions and avoids a redundant in-component sort. This formalizes the deviation recorded in 22-02-SUMMARY deviations[2].
- Empty state: when `cards.length === 0`, show centered muted text "No projects in this stage"

**Commit:** "feat(board): create KanbanColumn droppable component with header and card list"


> **Amendment (R02-QA):** Task 4's "DragOverlay card variant" is realized via the `isDragOverlay` prop on `KanbanCard` plus the exported `findCardById(cards, id)` helper in `KanbanCard.tsx`, rather than a separate overlay component. The parent `Board.tsx` looks up the active card with `findCardById` and renders `<KanbanCard isDragOverlay />` inside its `<DragOverlay>`. No separate overlay component was created. Rationale: same visual result with less duplication — reusing the single `KanbanCard` keeps overlay and in-column rendering in sync. This is a forward evolution of the planned approach, not a regression. This formalizes the deviation recorded in 22-02-SUMMARY.
