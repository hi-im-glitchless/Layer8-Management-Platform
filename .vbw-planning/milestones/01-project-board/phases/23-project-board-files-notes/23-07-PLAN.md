- For the Planner nav entry, wrap the rendered icon (or the entire `NavLink` content) in a `relative` container. When `count > 0`, overlay an absolutely-positioned dot:
  ```tsx

    <span
  ```

### Task 5 — Amendment (QA Round 01, resolved-by-amendment)

**Source FAIL ID:** `DEVN-07-01` (carried forward from 23-VERIFICATION.md → resolved by plan-amendment in `remediation/qa/round-01/R01-PLAN.md`).

**Status:** `resolved-by-amendment`. The original Task 5 spec text above (in particular the AC sentence naming "POST archive, PATCH notes, POST comment, file upload, and file delete" as the in-scope mutation matrix) is preserved verbatim for historical record; this amendment is purely additive and explicitly post-hoc. The indirect+grep coverage described below is declared **authoritative** for the file-upload and file-delete code paths in Phase 23.

**What was delivered (authoritative):**

`backend/src/services/__tests__/scheduleIsolation.phase23.test.ts` ships **6/6 passing test cases** — five per-mutation tests plus one cumulative full-mutation-matrix test. The five per-mutation cases cover:

1. `updateNotes` (PATCH `/cards/:cardId/notes`)
2. `editComment`
3. `softDeleteComment`
4. `createNotificationsForMentions`
5. `archiveCard` (POST `/cards/:cardId/admin/archive`)

The sixth cumulative case runs all five mutations against the same seed dataset before snapshotting, catching order-dependent regressions that per-test isolation would miss. **Each test asserts byte-equality** of the four schedule tables (`Assignment`, `TeamMember`, `Absence`, `Holiday`) before and after the mutation under test, with snapshots ordered by `id` to guarantee deterministic comparison. Verified by `npx vitest run scheduleIsolation.phase23.test.ts` → 6/6 pass.

**Why standalone file-upload + file-delete tests were not added:**

- **File upload:** exercising the upload path end-to-end requires multer/multipart plumbing through Express in-process or via supertest. That plumbing is non-trivial relative to the value it adds, given that the static-grep coverage (below) already locks the schedule-isolation invariant for the upload route at compile/grep time — a property strictly stronger than any single-shot runtime test could provide. Multer middleware initialisation, multipart body construction, and on-disk side-effect cleanup would expand the test fixture surface without exercising any new schedule-mutation call-site.
- **File delete:** already exercised **indirectly** via `archiveCard`'s `prisma.boardFile.deleteMany` call. The `archiveCard` test case in `scheduleIsolation.phase23.test.ts` asserts byte-equality of all four schedule tables across that operation, so the delete-path's schedule-isolation property is locked by the existing per-mutation test.

**Static-grep mitigation that locks the invariant for upload + delete:**

```bash
grep -nE "prisma\.(assignment|teamMember|absence|holiday)\.(create|update|delete|upsert|updateMany|deleteMany|createMany)" \
  backend/src/routes/boardFiles.ts \
  backend/src/services/boardFileService.ts
```

returns **zero matches** across both `boardFiles.ts` and `boardFileService.ts`. This is a **stronger guarantee** than a runtime test for the upload/delete code paths, because it forbids the existence of any schedule-mutation call-site at all — not merely that the call-site is unreachable on a particular runtime input. A reviewer touching either file and accidentally introducing a schedule-table write would surface the regression at grep/CI time before any test had to be re-run. The phase-wide schedule-isolation grep across all 11 Phase 23 backend files (referenced as AP-GLOBAL-01 in 23-VERIFICATION.md) extends the same property to the rest of the surface area.

**Follow-up:**

A standalone supertest-based upload+delete suite is a documented **optional follow-up**. The phase-wide schedule-isolation invariant is locked by (a) the runtime regression in `scheduleIsolation.phase23.test.ts` for archive (which exercises file delete via `prisma.boardFile.deleteMany`) and (b) the static grep on `boardFiles.ts` and `boardFileService.ts` for upload + delete. A future phase that needs end-to-end multipart-upload coverage for unrelated reasons (e.g. virus-scan integration regression, content-type negotiation) can fold in a standalone supertest harness at that point.
