1. **Install:** `cd /home/rl/Documents/Projects/Layer8/frontend && npm install react-markdown rehype-sanitize`. Confirm both appear in `dependencies`. No version pin beyond what npm resolves at install time.
2. **Extend `boardApi` in `frontend/src/features/board/api.ts`** with:
   ```ts
   updateNotes(cardId: string, notes: string) {
     return apiClient<{ card: { id: string; notes: string; notesUpdatedAt: string | null; notesUpdatedBy: string | null } }>(
       `/api/board/cards/${cardId}/notes`, { method: 'PATCH', body: JSON.stringify({ notes }) },
     )
   }
   async downloadFile(cardId: string, fileId: string): Promise<Blob> {
     const res = await fetch(`/api/board/cards/${cardId}/files/${fileId}/download`, { credentials: 'include' })
     if (!res.ok) throw new ApiError(res.status, `Download failed: ${res.statusText}`)
     return res.blob()
   }
   editComment(cardId: string, commentId: string, body: string) {
     return apiClient<{ comment: BoardComment }>(
       `/api/board/cards/${cardId}/comments/${commentId}`, { method: 'PATCH', body: JSON.stringify({ body }) },
     )
   }
   softDeleteComment(cardId: string, commentId: string) {
     return apiClient<{ success: boolean }>(`/api/board/cards/${cardId}/comments/${commentId}`, { method: 'DELETE' })
   }
   archiveCard(cardId: string, confirmProjectName: string) {
     return apiClient<{ success: boolean; cardId: string; projectName: string; fileCount: number; totalBytes: number }>(
       `/api/board/cards/${cardId}/admin/archive`, { method: 'POST', body: JSON.stringify({ confirmProjectName }) },
     )
   }
   getUnreadNotificationCount() {
     return apiClient<{ count: number }>(`/api/board/notifications/unread-count`)
   }
   markCardNotificationsRead(cardId: string) {
     return apiClient<{ success: boolean }>(`/api/board/notifications/mark-read`, { method: 'POST', body: JSON.stringify({ cardId }) })
   }
   ```
   Existing `addComment` should also accept an optional `mentions: string[]` (default `[]`) so the comment compose flow can pass mention IDs. Update its signature and the underlying request body to include `{ body, mentions }`.
3. **Update `frontend/src/features/board/types.ts`:** extend the `BoardComment` type with `isDeleted: boolean; editedAt: string | null; deletedAt: string | null;` and the `BoardFile` type with `scanStatus: string; isQuarantined: boolean;`. Add `notesUpdatedAt: string | null; notesUpdatedBy: string | null;` to `BoardCard`.

**Schedule isolation check:** none of these methods call schedule endpoints; verify `api.ts` does not import from `features/schedule`.

### Task 2: Extend hooks.ts with all Phase 23 mutation/query hooks
In `frontend/src/features/board/hooks.ts` add hooks following the existing pattern (`useMoveCard` at hooks.ts:~70 is the canonical reference — `onMutate` snapshot + cache patch, `onError` restore + handleMutationError, `onSettled` invalidate):

- **`useUpdateNotes`** — PATCH notes; optimistic update of `BoardCard.notes` + `notesUpdatedAt` in the `['board', 'cards', cardId]` cache; on error restore + toast.
- **`useDownloadFile`** — `useMutation` returning a Blob, with `onSuccess` triggering the browser download:
  ```ts
  onSuccess: (blob, { fileId, filename }) => {
    const url = URL.createObjectURL(blob)
    const a = Object.assign(document.createElement('a'), { href: url, download: filename })
    document.body.appendChild(a); a.click(); a.remove()
    URL.revokeObjectURL(url)
  }
  ```
- **`useEditComment`** — PATCH; optimistic body update + `editedAt` set client-side; on 403 surface `toast.error('Edit window expired')` (special-case the error message from the backend `WINDOW_EXPIRED` code).
- **`useSoftDeleteComment`** — DELETE (now soft); optimistic `isDeleted:true, body:null` patch; on error restore.
- **`useArchiveCard`** — POST; on success invalidate `['board', 'cards']` and toast `'Card archived'`; on `PROJECT_NAME_MISMATCH` toast `'Project name does not match'` (do not retry — surface the error to the dialog).
- **`useUnreadNotificationCount`** — `useQuery({ queryKey: ['board','notifications','unread'], queryFn: boardApi.getUnreadNotificationCount, refetchInterval: 60_000 })`. Used by plan 07's sidebar dot.
- **`useMarkCardNotificationsRead`** — mutation; on success invalidate `['board','notifications','unread']`. Used by CardDetailModal.

Each hook uses `handleMutationError(error, fallbackMessage)` in `onError`.

**Commit:** `feat(23-06): add hooks for notes, downloads, comment edit/soft-delete, archive, and notifications`

### Task 5 — Amendment (QA Round 01, resolved-by-amendment)

**Source FAIL ID:** `DEVN-06-01` (carried forward from 23-VERIFICATION.md → resolved by plan-amendment in `remediation/qa/round-01/R01-PLAN.md`).

**Status:** `resolved-by-amendment`. The original Task 5 spec text above (in particular the Comments-section bullet that sketches client-side `@mention` extraction against a known team-member list) is preserved verbatim for historical record; this amendment is purely additive and explicitly post-hoc. The data-path-only mention delivery described below is declared **authoritative for wave-3**.

**What was actually delivered (authoritative for wave-3):**

1. **Backend acceptance:** the comment-create endpoint accepts an optional `mentions: string[]` field (default `[]`) on the request body, per plan 23-04. Mentioned-user notification rows are still created end-to-end whenever a populated `mentions` array is supplied (covered by `createNotificationsForMentions` in `scheduleIsolation.phase23.test.ts`).
2. **Frontend API surface:** `boardApi.addComment` (in `frontend/src/features/board/api.ts`) was extended in this plan's Task 1 with the same optional `mentions: string[]` parameter (default `[]`); the request body now serialises `{ body, mentions }`.
3. **Modal compose form:** `CardDetailModal.tsx` (this plan's Task 5) wires the Comments compose flow to call `useAddComment().mutate({ cardId, body, mentions: [] })`, passing an empty array for the mentions field today. The backend → notifications path is fully connected — any client (a future UI, an external automation, or a server-to-server caller) can supply a populated array and the mention-notification side effect fires correctly.

**What was deferred and why:**

A roster-popover UI (the in-textarea `@`-trigger that surfaces a typeahead list of team members so the author can select mentions visually) requires a team-member **roster lookup**. Today, the only implementation of that roster lookup lives in `frontend/src/features/schedule` (the schedule team-members endpoint and its associated hooks/state). Pulling that roster across into the board feature would violate the **schedule-isolation** rule called out in `23-CONTEXT.md` ("Schedule Protection — NON-NEGOTIABLE"), which forbids the board feature from importing schedule-mutation code paths and from coupling board UI lifecycles to schedule-feature data flows.

The legitimate alternative — adding a new board-scoped roster endpoint that returns the team-member list independently of the schedule feature — is design and backend work that sits outside wave-3's scope. Wave-3 is the data-path wave; introducing a new endpoint on top of the already-deep set of plans 23-03/04/05/06 in this round would expand the surface area without serving the wave's stated goal of "wire the entire Phase 23 backend surface area into the frontend in one coordinated change".

**Follow-up tracking:**

The mention-authoring UX is a documented **Phase 23 follow-up**. A future phase that legitimately introduces a board-side roster endpoint (or alternatively, a thin type-only re-export of the schedule roster type that does not pull any schedule mutation code) can ship the popover at that point. Until then, the data-path-only delivery is sufficient because:

- The end-to-end notification side effect is exercised whenever any caller supplies a populated mentions array, and the backend behaviour for that path is locked by `scheduleIsolation.phase23.test.ts`'s `createNotificationsForMentions` case.
- 23-06-SUMMARY's `deviations` array entry 4 already documents the deferred UI transparently and names the schedule-isolation boundary as the explicit reason.
