## Upload Surfaces

The backend has **5 distinct multer-based upload surfaces**. Only one — **board card file uploads** — already carries an explicit, documented 500MB intent (`MAX_CARD_BYTES`), which is the strongest signal for which surface the milestone/bug report refers to ("Document Processing / Board file uploads" in the requirement mapping, `.vbw-planning/phases/02-fix-upload-size-limit/.context-scout.md:34`).

| Surface | Route file | Purpose | File types | Storage |
|---|---|---|---|---|
| **Board card files** | `backend/src/routes/boardFiles.ts` (mounted under `/api/board/cards/:cardId/files`) | Attach arbitrary evidence/artifacts to a kanban card | MIME allowlist (pdf, txt, csv, images, zip, docx/xlsx/pptx, octet-stream for `.ovpn`/`.conf`) | disk, `uploads/board/<cardId>/` |
| Documents (template→PDF) | `backend/src/routes/documents.ts` (`/api/documents/convert-pdf`) | Convert a DOCX template to PDF via Gotenberg | `.docx`, `.pdf` | disk, `uploads/documents/` |
| Executive Report wizard | `backend/src/routes/executiveReport.ts` (`/api/report/upload`) | Upload DOCX report source for sanitize/generate pipeline | `.docx` | memory (base64) |
| Template Adapter wizard | `backend/src/routes/templateAdapter.ts` (`/api/adapter/upload`) | Upload DOCX template for AI field mapping | `.docx` | memory (base64) |
| Profile avatar | `backend/src/routes/profile.ts` | User avatar image | image | disk |

The board-file surface is the one with a **pre-existing per-card 500MB quota** (`MAX_CARD_BYTES`, referenced in frontend UI copy "close to 500 MB" / "per-card 500 MB quota", `frontend/src/features/board/components/FilesPanel.tsx:38,69,107`) — i.e. the product already advertises 500MB to the user on this surface, but the **per-file** multer cap silently undercuts it at 50MB. This is the surface a ~200MB single-file upload would hit and the surface the milestone requirement ties to ("Document Processing / Board file uploads").

The other three multer surfaces (documents, executiveReport, templateAdapter) are all DOCX/PDF template-processing uploads, each independently capped at 50MB with no documented 500MB intent anywhere in code/comments — they are much less likely to be the surface the user tested (DOCX templates are rarely 200MB), but they use the *same* literal `50 * 1024 * 1024` value, so they should be called out as candidates the plan may need to decide on explicitly.

## Root-Cause Hypothesis

**Primary culprit: `MAX_FILE_BYTES = 50 * 1024 * 1024` in `backend/src/services/boardFileService.ts:16`, consumed by the board-files multer config at `backend/src/routes/boardFiles.ts:62`.**

Reasoning, ranked:
1. **Matches the exact symptom.** A ~200MB (209,715,200 bytes) file is well above the 50MB (52,428,800 bytes) multer `fileSize` limit on this route, and multer enforces `fileSize` per-file *before* the request completes — this produces exactly the "file-size-limit error" the user saw. The route's own error mapper produces the literal message `"File too large. Maximum size is 50MB."` (`boardFiles.ts:133`, HTTP 413, `multer.MulterError` with `code === 'LIMIT_FILE_SIZE'`).
2. **The 500MB intent already exists in the code/UI for this exact surface** — `MAX_CARD_BYTES = 500 * 1024 * 1024` (`boardFileService.ts:13`, sourced from "CONTEXT.md: Per-card quota: 500 MB hard cap") and the frontend UI literally shows "X MB / 500 MB" and toasts referencing "500 MB" (`FilesPanel.tsx:38,69,107`). The frontend's own upload gate (`FilesPanel.tsx:68`) only checks the file against the 500MB *card* quota — it has no independent per-file cap — strongly implying the product intent was "any single file up to 500MB is fine as long as the card isn't over quota," and the backend's `MAX_FILE_BYTES` was simply never raised to match when the 500MB card quota was introduced. The comment at `boardFileService.ts:15` ("Per-file size cap (mirrored from multer `limits.fileSize`)") reads as a stale/circular note rather than a deliberate 50MB product decision.
3. **The reverse-proxy layers (10) and (11) are real but secondary** — they would matter in the documented production/launcher deployment targets, but a ~200MB rejection with an app-level "file-size-limit" message (not a raw nginx 413 HTML page) is far more consistent with the multer-level rejection happening in dev (`launch-local.sh`, direct `npm run dev` on port 3001 with Vite proxy — no nginx in that path at all) or even in a deployed environment where multer still rejects first for anything class of file at all if it's ever above 50MB regardless of the proxy setting. Both nginx configs must still be fixed for the fix to hold end-to-end in deployed environments, but they are not the layer that explains "200MB rejected, 500MB expected" specifically — a proxy-level rejection at 10MB or 1MB would already fail far below 200MB and would look like a connection-level 413 from nginx, not an app JSON error.
4. **Express body parsers (item 7) are ruled out** — `express.json()`'s default 100kb limit only applies to JSON-typed request bodies; multipart file uploads are parsed by multer/busboy directly and never pass through the JSON parser.
5. **The other three 50MB multer configs (documents.ts, executiveReport.ts, templateAdapter.ts)** are plausible secondary findings (same stale 50MB constant) but have no 500MB intent documented anywhere and are DOCX/PDF template surfaces unlikely to see 200MB files in practice. Flag for the plan to explicitly decide in/out of scope rather than silently changing.

## Required Changes

To make the board-file upload path (and, if scoped in, the other DOCX/report upload paths) consistently support up to 500MB with only files over 500MB rejected and a clear message:

1. **`backend/src/services/boardFileService.ts:16`** — change `MAX_FILE_BYTES` from `50 * 1024 * 1024` to `500 * 1024 * 1024` (or simply drop the separate per-file constant and reuse `MAX_CARD_BYTES` for the multer `fileSize` limit, since a single file can never usefully exceed the card's total quota anyway — this removes the duplication that caused the drift in the first place). Update the stale comment at line 15.
2. **`backend/src/routes/boardFiles.ts:133`** — update the multer-error-map message from `"File too large. Maximum size is 50MB."` to reflect the new 500MB limit (e.g. `"File too large. Maximum size is 500MB."`), and consider distinguishing this 413 from the quota-guard 413 at line 110-115 with a differentiating field/code (e.g. `{ error: ..., reason: 'FILE_TOO_LARGE' }` vs `reason: 'QUOTA_EXCEEDED'`) so the frontend can show an accurate message instead of always saying "Quota exceeded."
3. **`frontend/src/features/board/components/FilesPanel.tsx:35-55`** — stop collapsing all 413s into "Quota exceeded…"; branch on the new distinguishing signal (or infer from `usedBytes`/`file.size` client-side, matching the pattern already used at line 68) so a single over-500MB file gets a message like `"File too large — maximum is 500MB."` while an actual per-card quota breach keeps the existing quota message.
4. **`deploy/nginx-layer8.conf:15`** — raise `client_max_body_size` from `10M` to `500M` (or `501M`/`520M` to give a small safety margin above the exact byte boundary for multipart overhead) so the documented systemd deployment doesn't clip uploads before they reach the app.
5. **`launcher.sh`** (inline nginx heredoc, `setup_nginx()`, around lines 242-287) — **add** a `client_max_body_size 500M;` directive to the `server { ... }` block (currently absent, defaulting to nginx's built-in 1MB), so the Cloudflare-fronted launcher path matches the same 500MB limit. Note: Cloudflare's own edge upload limit (100MB on Free/Pro plans, higher on Business/Enterprise) is outside this repo's control — if the deployed Cloudflare plan caps below 500MB, that's a platform-level constraint the plan/deploy docs should flag, not something fixable in this codebase.
6. **Decide scope on `documents.ts:26`, `executiveReport.ts:44`, `templateAdapter.ts:60`** — these three `MAX_FILE_SIZE = 50 * 1024 * 1024` constants are independent of the board-file fix. Recommend either (a) leave them at 50MB since DOCX/report templates are not expected to be 200-500MB and no product doc claims 500MB for them, explicitly noting this as an intentional scope boundary in the plan, or (b) if the plan owner wants one universal upload ceiling, raise all three to 500MB too and update their local error-message strings (`documents.ts:93`, `executiveReport.ts` — check for an equivalent message near its multer error handler, `templateAdapter.ts:193,262`) to match. Given the milestone's requirement mapping only names "Document Processing / Board file uploads" together, and only board files have documented 500MB intent, the default recommendation is **(a) board files only**, with (b) called out as a discussion point for the plan.
7. **`backend/src/routes/profile.ts:39-41`** (avatar, 2MB) — leave unchanged; explicitly out of scope (small image upload, unrelated to the 500MB requirement).
8. No change needed to `backend/src/index.ts` body-parser config (item 7 above, ruled out) or `frontend/vite.config.ts` dev proxy (item 12, not a factor).

## Test Conventions

- **Location/pattern:** Backend route tests live in `backend/src/routes/__tests__/`, one file per route module. The board-files suite is `backend/src/routes/__tests__/boardFiles.test.ts` — this is the natural home for a new size-limit regression test.
- **Runner:** Vitest 4 (`npm test` / `vitest run` from `backend/`), against the **real dev SQLite DB** (`vitest.config.ts` injects `DATABASE_URL`) — these are integration-leaning tests, not mocked.
- **Harness shape used by `boardFiles.test.ts`:** builds a minimal real Express app (`buildApp()`, `boardFiles.test.ts:102-115`) that mounts the actual `filesRouter` at `/cards/:cardId/files`, starts it on an ephemeral port (`startServer()`, line 117+), and drives it with plain `fetch()` calls using an `x-test-user` header to inject a fake session (bypassing full session/CSRF middleware, since those are tested elsewhere). Seed data (cards, files, users) is created per-test in `beforeEach` with a `withDbRetry` wrapper (lines 77-92) to absorb SQLite single-writer lock contention under parallel vitest workers, and cleaned up in `afterEach`.
- **Gap to fill:** no existing test in this file (or anywhere found) sends an actual multipart file body — the existing `(c)` 403 test (`boardFiles.test.ts:388-394`) POSTs with no body at all. A new test for the size-limit fix will need to:
  - Send a real `multipart/form-data` body via `FormData` + `fetch` (Node 18+/20+ native `fetch`/`FormData`/`Blob` support, consistent with existing `fetch`-based style) with a `Blob`/`Buffer` of controlled size.
  - Cover at least: (a) a file just under 500MB succeeds (or a smaller proxy value if actually allocating ~500MB in CI is impractical — consider asserting the multer config's exported constant equals `500 * 1024 * 1024` via a lightweight unit assertion, plus a functional test using a much smaller "boundary" size by temporarily wiring the route with an injectable limit, or accept a slower/larger test if the suite already tolerates it), and (b) a file over 500MB is rejected with 413 and the corrected message.
  - Given CI cost of allocating true 200-500MB buffers, a pragmatic approach the plan should consider: keep `MAX_FILE_BYTES` as an exported, testable constant (already true) and add a **unit-level** assertion (`expect(MAX_FILE_BYTES).toBe(500 * 1024 * 1024)`) plus one **functional** boundary test using a small multiple of KB/MB against a **test-only reduced limit** if the route/service is refactored to accept an injected limit — otherwise a real large-buffer test guarded to run only when explicitly requested (e.g. tagged/skipped by default) may be the least disruptive option. Flag this test-strategy decision explicitly for the plan.
- **Sanitization service (Python/pytest)** is unrelated to this bug (no file-size logic there) — not a test target for this fix.
- **Frontend tests:** frontend test coverage is sparse repo-wide (`TESTING.md`); no existing tests for `FilesPanel.tsx`. If the plan chooses to fix the misleading 413→"Quota exceeded" message (Required Changes #3), a small `vitest`/`@testing-library` test could assert the correct toast per error variant, but this is optional given the frontend's current low test coverage norm — note this as a nice-to-have, not a blocker.
